# ADR-0007: Module identity and JPMS

- **Status:** Accepted
- **Date:** 2026-11-15
- **Deciders:** project owner
- **Supersedes:** none

## Context

The artifact is a JVM library published to Maven Central and used both from the
classpath and, potentially, from the module path. Kotlin does not emit
`module-info.class`; the Kotlin compiler produces ordinary class files and
Kotlin metadata. A JAR without `module-info` still gets a module name on the
module path, but that name is derived from the JAR filename unless the manifest
declares `Automatic-Module-Name`. Filename-derived names are unstable across
build systems and publication tooling.

Full JPMS support would require a `module-info.java` compiled into the same
artifact as Kotlin classes. With this build that means a second compilation
(Java source set or a separate `javac` invocation), duplicate API surface
checking, and a build that is materially more complex for every contributor.

The package root is shared with version 1 (ADR-0001), so a module path that
contains both versions would have the same packages in two modules, which the
module system rejects as a split package.

## Decision

We will set **`Automatic-Module-Name: com.psiwray.organization.terminal_window`**
in the JAR manifest, and we will not ship `module-info.class` in 2.0.

The name matches the package root and is applied by the build (section 18), not
by hand-editing the JAR. It is part of the published contract: renaming it is a
breaking change.

Full JPMS is deferred. The conditions for revisiting it are:

- a build that can compile `module-info.java` against the Kotlin output without
  a dual-source layout, and
- a module descriptor whose name, exported packages, and `requires` clauses
  preserve the automatic module's observable behavior.

Until then, consumers on the module path get an automatic module: it exports
all packages, reads all modules, and has no `requires transitive` information.
Consumers on the classpath are unaffected.

## Consequences

### Positive

- The module name is explicit and stable regardless of the JAR filename or the
  build directory.
- No second compilation, no `module-info` maintenance, and no divergence between
  Kotlin and Java views of the same packages.
- Classpath consumers, which are the majority, see no difference at all.
- The name is aligned with the package root, so tools that derive one from the
  other agree.

### Negative

- Automatic modules export `internal` Kotlin declarations at the JVM level;
  JPMS cannot hide them, just as it cannot hide them on the classpath.
- The module reads every other module, so missing `requires` errors are
  discovered only at runtime as `NoClassDefFoundError`, not at module
  resolution.
- No `requires transitive` means consumers must declare LWJGL and JOML modules
  themselves.
- A future `module-info` may need to export only the public packages, which
  changes the observable module surface and therefore requires a major version
  or careful compatibility analysis.
- Version 1 and version 2 cannot coexist on the module path: same packages, two
  modules, split-package error. This is the desired fail-fast behavior.

### Neutral

- The automatic module name does not affect the Maven coordinates or the POM.
- The manifest entry is generated by the build; section 18 owns the exact
  configuration and the verification that the entry is present.
- Dokka and source jars are unaffected.

## Alternatives

| Alternative | Why rejected |
|---|---|
| No `Automatic-Module-Name` | The module name becomes filename-derived and changes with artifact renaming or shading. |
| Full `module-info.java` now | Requires a dual-source build or a separate Java compilation, duplicates API checks, and slows every contributor for no 2.0 requirement. |
| Multi-release JAR with a versioned `module-info` | Adds packaging complexity and tooling support requirements; the module descriptor would still need a Java compilation. |
| Rename packages to match a new module | Breaks the version 1 package root requirement and forces consumers to rename imports. |
| Shade dependencies into the JAR | Hides LWJGL natives and licenses, and creates a merged module with unreviewed contents. |
